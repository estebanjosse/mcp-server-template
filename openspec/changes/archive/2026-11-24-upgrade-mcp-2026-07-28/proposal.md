# Change: Upgrade to MCP 2026-07-28 and the official C# SDK 2.4.0

## Status

Unreleased migration checkpoint. This branch incorporates main at `6436000` (PR #66) and now uses SDK 2.4.0; the published template 1.4.0 still embeds SDK 1.3.0. Task 2.5 onward, merge, release and deployment are not authorized. Read the [approval checklist](approval.md) before authorizing implementation. See [design](design.md) and the [draft user migration guide](../../../docs/migrations/mcp-2026-07-28.md).

## Why

The published template 1.4.0 embeds SDK 1.3.0, whose newest protocol revision is 2025-11-25. The latest stable protocol and SDK introduce a different negotiation/session model, security fixes and new extension boundaries. A package-only upgrade could change behavior without a compile error. Owners of previously generated applications need a simple guide if they choose to upgrade; a new template release does not require them to migrate.

## What Changes

- Propose SDK 2.4.0 for all MCP packages and reconcile its actual published dependency floors while retaining .NET 10.
- **BREAKING**: make HTTP session policy explicit for the upgraded template. Recommend stateless for newly generated projects. Do not implement or document hybrid compatibility as a migration path. Existing deployments that depend on sessions must migrate before adopting the upgraded host.
- Qualify modern discovery/per-request metadata and down-level initialize flows separately over HTTP and stdio.
- Update transport/error/schema/cache assertions, SDK-dependent examples, protocol documentation and packaging checks.
- **BREAKING**: replace the misleading active-session metric with request-in-flight telemetry and document dashboard/alert migration. Preserve and extend the C#/xUnit host and packed-template tests added by #66; retire superseded characterization scripts within the approved validation task.
- Supply a simple English step-by-step guide for owners who voluntarily migrate an application generated by an older template. Separate advanced compatibility/security cases from the main path; do not regenerate or automatically update existing applications.
- Record a separate, deferred feature-showcase backlog. Core migration approval does not authorize new Tasks, Apps, Skills or interactive examples.

## Capabilities

### New Capabilities

- `mcp-protocol-compatibility`: version-aware transport behavior, supported client matrix, dependency alignment and wire-level acceptance evidence.
- `generated-project-migration`: explicit manual upgrade and rollback guidance for existing applications, with tested fresh-project comparison.

### Modified Capabilities

- `metrics-observability`: replace session-labelled concurrency with precisely scoped request-in-flight telemetry, including failure/cancellation and authentication-boundary scenarios.

Existing `ci-pipeline`, `developer-docs` and `dotnet-template` requirements remain in force. Extend their implementation/tests without changing guarantees; add explicit deltas before any subsequently approved requirement change. The July proposal is superseded as an implementation plan, not merged wholesale.

## Impact

Affected areas: `Directory.Build.props`, the HTTP/stdio hosts, MCP adapter serialization/registration, HTTP protocol tests, generated-project validation, relevant CI, docs and template packaging. Application services and domain DTOs do not require redesign based on inspected code. Existing auth, hardening, observability and QA proposals remain separate; reference them rather than implementing their full scope here.
